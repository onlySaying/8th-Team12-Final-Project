# 미니게임 구현 방식 정리

햄버거집 알바 미니게임(기획 HTML 시안 `play.html`)을 언리얼로 옮기면서 검토한 방식들과,
지금 채택한 구조를 정리한다. 꽃집 · 편의점(서바이버) 미니게임도 같은 틀을 쓴다.

> **2026-10-18 진입 방식 변경** (코드 확인: `MiniGameSettings.cpp`, `MiniGameSubsystem.cpp`, `DialogueSubsystem.cpp`, `MiniGameDoor.cpp`)
> 처음에는 가게 맵(`L_BurgerHouse`, `FlowerHouse`)으로 이동한 뒤 미니게임이 시작됐다. 가게를 채울 직원 · 손님 모델이 없어 빈 가게를 걷는 시간만 늘어서,
> **가게 맵 2개와 손님 AI 코드를 지우고** 본편 대화의 `StartMiniGame <키>` 액션이 **레벨 이동 없이 지금 레벨에서** 띄우도록 바꿨다 (같은 커밋에서 `L_ConvenienceStore` 맵도 삭제).
> 문(`AMiniGameDoor`) → 레벨 이동 경로는 테스트 맵 `L_MiniGameTest`용으로만 남아 있다.

## 1. 지금 구조 (채택)

### 1-1. 흐름 — 본편

```
[본편 레벨] 아침 선택지에서 가게를 고름
  DT_StoryDialogue: @GrantTag Today.Work → @FadeOut → @TimeSetSchedule Schedule.AfterSchool
                    → @StartMiniGame Burger | Flower | L_ConvenienceStore

  UDialogueSubsystem  (EGameActionType::StartMiniGame)
    └─ UMiniGameSubsystem::StartHere(Action.Key)
         ├─ MiniGame Setting의 Levels에서 키를 찾는다 (없거나 이미 진행 중이면 실패)
         ├─ bStartedHere = true  (레벨 이동 없이 띄웠다는 표시)
         └─ 0.5초 뒤 TryStart  (대화가 끝나 입력이 풀린 다음 위젯이 입력을 가져가도록)

  TryStart → StartMiniGame
    ├─ 행동력(AP)이 남아 있어야 시작, AP 1 소모
    ├─ 캐릭터 이동 · 시점 입력 잠금, 입력 모드 UI 전용, 마우스 커서 표시
    ├─ 단색 배경 UMiniGameBackdropWidget (Z 49, 설정의 BackdropColor)
    ├─ 미니게임 위젯 생성 → AddToViewport(50)
    └─ BGM 재생 (설정에 있으면)

  위젯: 플레이 → FinishGame() → 보상 지급 (한 판에 한 번)
        결과 확인 → ExitGame()

  UMiniGameSubsystem::EndMiniGame
    ├─ 위젯 · 배경 제거, BGM 페이드아웃, 입력 원복
    └─ 본편 레벨이면 DemoFlow::OnMiniGameEnded → 그날 밤(Schedule.Night)으로 맞추고 방(Room) 레벨로
```

- 세 미니게임 모두 설정에서 `bMovePlayer = False`, `bUseFixedCamera = False`. 고정 카메라 기능(`bUseFixedCamera`, 런타임에 `ACameraActor` 생성)은 남아 있지만 지금은 쓰지 않는다 — 배경 위젯이 화면을 덮기 때문.
- 본편 레벨 판정은 `L_MiniGameTest`, `FreeLoad`(타이틀)가 아닌 모든 레벨.

### 1-2. 흐름 — 테스트 맵 (`L_MiniGameTest`)

```
AMiniGameDoor  ── E키 상호작용 (AP > 0, InteractConditions 충족) ──▶
  ├─ MiniGameKey가 있으면  → StartHere(MiniGameKey)   (레벨 이동 없음, 끝나면 그 레벨에 그대로)
  └─ 없으면 TargetLevel로 이동
       ├─ UMiniGameTravelSubsystem::SetReturnPoint (지금 서 있는 자리)
       ├─ SetMinigameBooking(true) → OpenLevel(TargetLevel)
       ├─ 도착 레벨의 UMiniGameSubsystem::OnWorldBeginPlay가 예약을 보고 TryStart
       └─ 끝나면 ReturnToPreviousLevel → 돌아오면 ReturnPoint에 세운다
```

- 돌아올 때 PlayerStart가 아니라 들어간 자리에 세우는 이유: PlayerStart가 행인 경로 위면 돌아오자마자 행인 무리에 밀려 혼자 움직이는 것처럼 보였다.

### 1-3. 구성 요소

| 파일 (`Source/Febricula/.../MiniGame/`) | 역할 |
|---|---|
| `MiniGameSettings` | Project Settings > MiniGame Setting. **키 → 미니게임 위젯 · 시작 위치 · 배경색 · BGM · 보상** 표 (`DefaultGame.ini`) |
| `MiniGameTypes` | `FMiniGameLevelEntry`(설정 한 줄), `FMiniGameResult`, `FMiniGameReward` |
| `MiniGameSubsystem` | 띄우기(`StartHere` / 레벨 시작 시), 입력 잠금, 보상 지급(중복 방지), 끝난 뒤 처리 (World 서브시스템) |
| `UMiniGameTravelSubsystem` (`MiniGameSubsystem.h`에 같이 선언) | 이전 레벨 · 돌아올 자리 · 미니게임 예약 기억 (GameInstance 서브시스템 - 레벨을 넘어가도 유지). 테스트 맵 경로용 |
| `MiniGameWidget` | 위젯 베이스. `FinishGame` / `PreviewReward` / `ExitGame` |
| `MiniGameBackdropWidget` | 미니게임 뒤에 까는 단색 배경 (에셋 없이 C++로 위젯 트리 구성) |
| `MiniGameDoor` | 테스트 맵용 문. `MiniGameKey`(지금 레벨에서 시작) 또는 `TargetLevel`(레벨 이동). 기존 `InteractionComponent`가 그대로 감지 |
| `Burger/BurgerMiniGameWidget` | 햄버거 게임 규칙 + 화면 (`NativePaint`) |
| `Flower/FlowerMiniGameWidget`, `Flower/FlowerPhysics.h` | 꽃집 게임 + 강체 물리 |
| `Survivor/SurvivorMiniGameWidget` | 편의점 야간 알바 (뱀파이어 서바이버 풍) |

### 1-4. 화면을 그리는 방식 — 위젯 트리 없는 C++ 위젯

```
화면(Viewport)
 ├─ PlayerHUDWidget            기존 HUD (손대지 않음)
 ├─ MiniGameBackdropWidget     Z-order 49, 화면 전체 단색
 └─ BurgerMiniGameWidget       Z-order 50
     └─ 840×1240 가상 캔버스를 화면 높이에 맞춰 가운데 배치 (양옆은 배경색)
```

- WBP 디자이너에 이미지·텍스트를 배치하지 않는다. `NativePaint`에서 배경 · 주문판 · 재료 · 캐릭터를
  **HTML 캔버스와 같은 좌표·크기 숫자**로 직접 그린다 (`FSlateDrawElement::MakeBox / MakeText`).
- 키보드는 위젯이 직접 받는다 (`NativeOnKeyDown`). 버튼은 그림 + 마우스 영역 판정.
- 텍스처 26장: `/Game/MiniGame/Burger/Textures/` (최근접 필터 · 밉맵 없음 · UI 압축).
- 편의점(서바이버)은 넓을수록 재미있어서 가로 화면(2200×1240) 전체를 매장 바닥으로 쓴다.
- 가게 맵이 있던 시절에는 양옆을 투명하게 두고 3D 햄버거집(손님 NPC)을 배경으로 보여 줬다. 맵을 지우면서 단색 배경으로 바꿨다.

### 1-5. 이 구조를 고른 이유

| 이유 | 설명 |
|---|---|
| 남의 맵을 안 건드린다 | 미니게임 종류 · 보상을 **설정(ini)** 에 두고 대화 데이터가 키로 부른다. 레벨에 액터를 놓지 않으니 다른 사람 맵 파일을 저장할 일이 없다 |
| HTML 시안을 숫자 그대로 옮긴다 | 좌표계가 같아서 기획이 시안을 고치면 숫자만 옮기면 된다 |
| 3개 게임이 틀을 공유 | 시작 · 정산 · 복귀는 공통. 게임마다 위젯 클래스 하나 + 설정 한 줄만 추가한다 |
| 에디터 연결 없이 개발 가능 | WBP 작업이 없어 코드만으로 빌드 · 수정 · 디버그 |
| 플레이 흐름이 짧다 | 선택지 → 바로 미니게임 → 끝나면 그날 밤 방으로. 빈 가게를 걸어 다니는 구간이 없다 |

## 2. 검토한 방식 비교

### 2-1. 어디에 띄우나

| 방식 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **A. 기존 HUD 안에 넣기** | `PlayerHUDWidget`(WBP)의 Overlay에 미니게임 패널을 추가하고 보이기/숨기기 | 위젯이 하나라 Z-order 관리가 쉽다 (HUD 설계 의도와 같음). 대화창과 같은 스타일 공유 | **HUD WBP가 공용 파일** — 대화 · 프롬프트 담당과 충돌. HUD가 미니게임 3개 내용을 다 품어 비대해진다. 미니게임 없는 레벨에도 항상 로드 |
| **B. 별도 위젯을 Viewport에 추가** (채택) | 미니게임 위젯을 따로 만들어 HUD 위(Z 50)에 띄우고, 끝나면 제거 | HUD와 완전히 분리 — 서로 수정이 안 부딪힌다. 필요할 때만 생성. 게임별 교체가 쉽다 | Z-order를 신경 써야 한다 (HUD 프롬프트가 위로 올라오지 않게). 입력 모드 전환을 직접 관리 |
| C. AHUD 캔버스 (`DrawHUD`) | 게임모드의 HUD 액터에서 `Canvas->DrawTexture`로 그리기 | UMG 없이 가장 단순한 즉시 그리기 | **게임모드 HUD 클래스를 바꿔야 한다** (공용). 클릭 · 포커스 · 해상도 대응을 전부 직접. UE4식 구식 방법 |
| D. 월드에 배치 (Paper2D / 액터) | 레벨 안에 스프라이트 · 카메라를 놓고 2D 게임처럼 | 조명 · 파티클 등 3D 연출 가능 | **맵 파일을 수정**해야 함. 카메라 전환 · 충돌 · 해상도 대응이 무겁다. 2D UI 게임에 과함 |
| E. 미니게임 전용 레벨 | 빈 레벨에서 미니게임만 실행 | 다른 시스템과 완전 격리 | 햄버거집 배경(손님 NPC)을 못 쓴다. 레벨이 3개 더 늘어난다 |

**HUD에서 띄우는 것(A)도 가능하다.** HUD가 이미 "한 위젯 안의 Overlay로 쌓는다"는 설계라
패널 하나를 더 얹으면 된다. 다만 HUD는 대화 시스템 담당 파일이고, 미니게임 3개를 다 넣으면
충돌과 비대화가 커서 B를 골랐다. B도 HUD 위에 겹쳐 뜨므로 화면상 결과는 같다.

> 위 비교는 가게 맵이 있던 시점 기준이다 (E의 "햄버거집 배경" 단점 등). 진입 방식이 바뀐 뒤에도 B 구조는 그대로라 `StartHere` 추가만으로 전환됐다.

### 2-2. 화면을 어떻게 그리나

| 방식 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **① C++ `NativePaint` 직접 그리기** (채택) | 위젯 트리 없이 C++에서 좌표로 그린다 | HTML 캔버스 코드와 1:1 대응 — 이식이 빠르다. 떨어지는 재료 수십 개처럼 **수가 변하는 오브젝트에 유리** (위젯 생성/삭제 없음). 에디터 없이 개발 | 디자이너가 화면에서 끌어다 고칠 수 없다 (숫자 수정). 레이아웃 변경마다 컴파일 |
| ② WBP 디자이너 + C++ 로직 | `BindWidget`으로 Image/TextBlock을 연결, 로직만 C++ | 디자이너가 직접 배치 · 폰트 · 애니메이션 편집. UMG 기능(애니메이션, 스타일) 그대로 사용 | 떨어지는 재료처럼 **동적 오브젝트는 위젯을 매번 생성/풀링**해야 한다. WBP는 바이너리라 git 충돌 시 병합 불가. MCP/에디터 작업 필요 |
| ③ 혼합: ① 상속 WBP | ①의 C++ 위젯을 부모로 WBP를 만들고 장식만 WBP에 얹기 | 게임 화면은 코드, 프레임 · 타이틀 연출은 디자이너가 | 두 곳을 봐야 한다 |
| ④ Web Browser 위젯 | HTML을 그대로 띄우기 | 이식 작업 0 | **WebBrowser 플러그인(CEF) 필요**, 패키지 용량 · 시작 시간 증가. 입력 포커스 · 보상 연동(JS↔C++)이 불안정. 콘솔 미지원 |

**지금은 ①로 만들고, 아트 연출이 필요해지면 ③으로 확장**할 수 있다
(예: 타이틀 화면만 WBP 애니메이션).

## 3. 보상 · 데이터

### 3-1. MiniGame Setting 키 (`MiniGameSettings.cpp` 기본값 + `DefaultGame.ini`)

| 키 | 위젯 | 돈 | 스탯 | 스탯 구간 (점수 ≥ 값마다 +1, 기본 1 → 1~5) | 점수 |
|---|---|---:|---|---|---|
| `Burger` | `BurgerMiniGameWidget` | 40,000 | `HandWork` (손재주) | 3, 5, 7, 9 | 완성 주문 수 |
| `Flower` | `FlowerMiniGameWidget` | 30,000 | `Health` (체력) | 7, 10, 12, 14 | 완료 주문 수 |
| `L_ConvenienceStore` | `SurvivorMiniGameWidget` | 30,000 | `Speech` (말솜씨) | 55, 80, 100, 120 | 퇴점시킨 손님 수 |

- 편의점 키는 원래 레벨 이름 키였다(레벨이 열리면 자동 시작). 맵은 지워졌지만 키 이름은 그대로 두고 `StartMiniGame L_ConvenienceStore`로 부른다.
- 키는 "레벨 애셋 이름(경로 없이)" 또는 "`StartMiniGame` 액션이 쓰는 이름" 둘 다 될 수 있다 (`UMiniGameSettings::Levels` 주석).

### 3-2. 공통 규칙

| 항목 | 값 | 위치 |
|---|---|---|
| 돈 | 키별 고정값 (기획 확정) | `GameProgressSubsystem` 카운터 `Money` (아직 돈 시스템이 없어 카운터 사용, `MoneyCounterId`) |
| 스탯 | 기본 1 + 점수가 구간 값 이상일 때마다 +1 | `GameProgressSubsystem` 스탯 (`PreviewReward`가 계산) |
| 지급 시점 | 한 판에 한 번 (`GrantReward` 중복 방지, 두 번째부터는 지급했던 값을 그대로 반환) | `MiniGameSubsystem` |
| 플레이 횟수 | 끝까지 한 판만 센다 (건너뛰기 제외). 카운터 `MiniGame.<키>.Played`. 0이면 설명 카드, 1 이상이면 건너뛰기 허용 | `MiniGameSubsystem::GetPlayCount` |
| 시작 조건 | AP > 0, 시작 시 AP 1 소모 | `TryStart` / `StartMiniGame` |
| 수치 변경 | Project Settings > MiniGame Setting > Levels > 키 | `DefaultGame.ini` |

### 3-3. 꽃집 (`Flower`, `Flower/FlowerMiniGameWidget`)

| 항목 | 값 |
|---|---|
| 규칙 | 90초. 같은 꽃 둘이 닿으면 다음 단계(씨앗→…→꽃다발). 떨어지는 꽃은 씨앗~튤립 4종. 주문 묶음의 꽃이 작업대에 동시에 모두 있으면 한꺼번에 포장(떨어뜨린 꽃도 인정, 같은 꽃끼리 닿으면 합쳐지니 지켜야 한다). 위험선(y 520) 위 2초면 종료 |
| 물리 | `Flower/FlowerPhysics.h` — 꽃 그림 실루엣에 맞춘 원 3~5개짜리 강체(회전 · 마찰 · 반발). 원 하나로 다루면 깔끔하게만 쌓여서 바꿨다. 언리얼 타입 없는 헤더라 난이도 시뮬레이터가 그대로 쓴다 |
| 주문 순서 | 튤립×2 → 장미+튤립 → 해바라기+튤립 → 장미×2 → 해바라기+장미+튤립 → 튤립×3 → 수국+장미 → 해바라기×2 → 수국+해바라기+튤립 → 꽃다발+장미 (튤립×3부터 반복) |
| 점수 | 완료한 주문 수 (꽃다발 둘을 합친 특대 꽃다발도 1건 — HTML의 700원 보너스 대신) |
| 돈 | 30,000 고정 (기획 확정) |
| 체력 | 기본 1 + 완료 주문 수가 {7, 10, 12, 14}에 닿을 때마다 +1 → 1~5 (`Health`). 시뮬레이션: 천천히 9건 · 쉬지 않고 11~13건 · 14건은 드묾 |
| 튜토리얼 | 첫 판은 연습 판 5단계(놓기 → 합치기 → 데이지 → 튤립 주문 → 위험선), 이후 설명 카드 3장 · 대충 일하고 퇴근 |
| 시작 | 본편: 아침 선택지 → `StartMiniGame Flower` (지금 레벨에서). 테스트: `L_MiniGameTest`의 문 |

## 5. 새 미니게임 추가 방법

1. `UMiniGameWidget`을 상속한 위젯 클래스를 만든다 (규칙 + `NativePaint`).
2. 끝날 때 `FinishGame({Score})`, 결과 확인 버튼에서 `ExitGame()`.
3. MiniGame Setting > Levels에 `키 → 위젯 클래스 · 배경색 · BGM · 보상` 한 줄 추가.
4. 본편: 대화 데이터에 `@StartMiniGame <키>`. 테스트 맵: `MiniGameDoor`의 `MiniGameKey`에 키 지정 (또는 `TargetLevel`로 레벨 이동).

시작 · 입력 전환 · 보상 지급 · 끝난 뒤 처리는 공통 코드가 한다.
